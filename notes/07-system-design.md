# 系统设计

## 场景设计题：智能客服 Agent

### 需求

处理用户退换货请求，需要查询订单、判断退换货资格、生成退换货单、通知用户

### 架构设计

```
用户消息 → [路由器] → [意图识别] → [信息收集] → [业务处理] → 回复用户
              │                         │
              ├─ 退换货意图             ├─ 订单号
              ├─ 咨询意图               ├─ 退换原因
              ├─ 投诉意图               ├─ 商品状态
              └─ 闲聊                   └─ ...
```

### 关键组件

1. **意图路由**：一级分类 + 二级细分
2. **槽位填充**：逐步收集必要信息，支持多轮对话
3. **工具体系**：
   - `query_order(order_id)` — 查订单
   - `check_return_eligibility(order_id)` — 检查退换资格
   - `create_return(order_id, reason)` — 生成退换单
   - `send_notification(user_id, message)` — 通知用户
4. **异常处理**：订单不存在、超退换期、商品异常等
5. **升级机制**：Agent 处理不了时升级到人工客服

## 场景设计题：代码审查 Agent

### 核心能力

- 解析 PR diff
- 理解代码意图
- 发现 Bug / 安全漏洞 / 性能问题
- 给出具体修改建议

### 架构

```
PR Webhook → 拉取 diff → 分文件分析 → 汇总评审意见 → 评论到 PR
                  │
                  ├─ 每个文件独立分析（并行）
                  │    ├─ Bug 检查
                  │    ├─ 安全扫描
                  │    ├─ 性能分析
                  │    └─ 代码风格
                  │
                  └─ 汇总 + 去重 + 按严重性排序
```

### 挑战

- 大 PR diff 超 context → 分文件/分块处理
- 缺少项目上下文 → 注入项目 README、代码规范文档
- 误报 → 区分 "必须修改" 和 "建议优化"

## 场景设计题：多 Agent 协作完成复杂任务

### 场景：软件开发 Agent 团队

```
┌──────────────┐
│  产品经理 Agent │ → 需求分析 → 拆分为 Task
└──────┬───────┘
       │
┌──────▼───────┐
│  架构师 Agent  │ → 技术方案 → 模块划分
└──────┬───────┘
       │
┌──────▼───────┐
│  开发 Agent ×3 │ → 并行开发各自模块（通过 worktree 隔离）
└──────┬───────┘
       │
┌──────▼───────┐
│  审查 Agent   │ → 代码审查 → 反馈 → 修改
└──────┬───────┘
       │
┌──────▼───────┐
│  测试 Agent   │ → 写测试 → 运行 → 报告
└──────────────┘
```

### 关键设计决策

| 问题 | 方案 |
|------|------|
| 状态同步 | 共享任务看板（结构化 JSON） |
| 冲突解决 | 审查 Agent 统一裁决 |
| 成果交付 | 每个 Agent 输出到独立目录，最终合并 |

## 架构模式总结

### 单 Agent vs 多 Agent

- **单 Agent**：简单可靠，适合大多数场景
- **多 Agent**：复杂任务、需要多视角、独立可并行子任务

### 选择依据

```
任务复杂度
  ├─ 简单（查天气、问答）     → 单 Agent + 简单工具
  ├─ 中等（订机票、客服）     → 单 Agent + 多工具 + 流程控制
  └─ 复杂（软件开发、研究）   → 多 Agent 协作 + 工作流编排
```
